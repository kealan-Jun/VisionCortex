## 不改变的生产边界

- 设备日五目录、媒体身份、时间语义、关键帧与场景帧区分、原始录音保留不变。
- 不删除原片，不启用尚未通过原生NAS软链接验收的清理功能。
- 精扫使用已接受的 batch 4 引擎；batch 16 候选仍需同输入质量和性能对照。
- 理解、日报维持现有暂停设置；其待处理需求不能被算作全链路成功。
- 扫描与召回代码指纹变化后，相关视觉产物遵守原有版本校验；历史复算单独计数，不充作新增实时吞吐。不扩充历史回执兼容名单来代替新版本验证。
- 只在独立工作树测试。上线切换与持续观测须单独记录，不以代码同步代替部署证明。

## 验收方式

确定性检查覆盖等待与恢复、真正失败预算、来源漂移、活动租约、超过50条观测、
错误心跳、读取器关闭及质量门禁。使用生产Python 3.12运行隔离测试，模型以替身验证，
这些检查不代表真实实验识别准确率。

实际吞吐按同一连续观察窗口统计到达、成功发布、真实模型执行和缓存复用，区分实时输入
与历史补跑。10台设备每小时各4片对应40片/小时；11台同频率输入对应44片/小时。
连续8–12小时负载下，完成量覆盖到达量、可处理待办与等待时间不持续增长，才有依据评估
持续处理能力。没有新增采集、服务中断、只完成粗扫、只看到GPU活动均不能替代此验收。

本轮观察到其他任务为了训练切换同一服务，相关中断必须保留并切断连续验收窗口。
运行时证据存放在本机 `Runtime/ProcessingRecovery-20260923`，不提交数据库、视频、
模型、引擎或生产回执到Git。

## 392f0b8 上线后的第二轮修复

以下问题来自 `392f0b8` 运行后的继续复核。实现于独立恢复工作树；修改和本地
检查期间没有停止线上服务。该段记录代码机制，实际部署 SHA 与运行结果仍以
本机独立部署回执为准。

### 解码和推理初始化

- 原有 CUDA 解码限制只覆盖粗扫任务偏好。精扫每任务 4/6 个解码 worker
  叠加后，实际 FFmpeg 子进程没有总量约束。新增本地运行根与 GPU 编号共同
  定位的跨进程槽位，默认总量 6；溢出的解码请求立即使用 CPU。槽位随实际
  子进程存活，取消、失败、关闭和父进程退出不能提前释放仍存活的子进程槽位。
  实际后端单独记录。此约束不覆盖其他运行根或独立训练程序，6 也不是已验证
  的最佳吞吐参数。
- Ultralytics 对引擎读取 `Model.names` 会创建临时 predictor，首次推理
  又创建持久 predictor。改为在推理所属线程创建并保留 predictor，类别和
  分支校验、warmup 完成后才将共享实例标为就绪。扩容阶段的真实初始化失败
  因此能回退到已有同身份健康实例；首个或全部实例失败仍如实失败。warmup
  不计入视频处理帧数或模型证据。

### 召回门控的含义与故障恢复

现有 10% 门槛计算的是抽中帧的执行失败比例，不能解释为物理动作准确率或
召回率。正常推理得到空预测、没有手与物体接触均可通过；不可读帧和模型执行
异常才计为错误。每小时通常仅选 2–8 帧，一帧未恢复错误就会超过该门槛。
此前整项重试在复用粗扫账本后仍重复执行召回，三次尝试可能连续遇到同一故障。

恢复应保持同一选中时间、同一模型和识别参数，在失败步骤内有界执行：读帧
重新打开句柄，模型异常只恢复失败模型；已成功执行的另一模型无需重做。
CUDA 显存不足的 CPU 路径必须明确记录真实设备和原因，不得冒充 GPU 执行。
最终错误率按仍未恢复的选中帧计算，恢复前失败次数另记。持续失败、取消、
资产或配置不满足要求不能制造成功证据，也不能扩大容错率来掩盖缺失。

失败报告同时保留至本地运行根的 `device-day/RecallFailures`，包含选中帧、
具体失败类型及计划身份；不写入成功计划缓存。该记录用于后续判断真实失败率
是否下降，单纯生成记录不是问题已解决的证明。

`PROVEN` 的边界是代码及确定性替身测试；真实 GPU 稳定性、恢复路径在实际
视频上的质量，以及连续 8–12 小时不积压仍须独立验证。两次定点 CPU 读帧
成功仅证明旧任务两个历史选中时刻现在可读，不能排除此前瞬时 I/O 或推理异常。
