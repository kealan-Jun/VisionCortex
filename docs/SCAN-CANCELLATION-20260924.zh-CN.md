# 扫描失败后的解码回收

2026-09-24，基于生产代码 `49977f8`。当前生产检测仍为第一人称 v8、第三人称精扫 v5m / 粗扫 v2。本改动不更换权重、不改变 GPU 配额或采集服务。

## 问题与修复

07:09:32 CST，分析进程 1223974 被系统全局 OOM 终止，内核记录匿名 RSS 26,241,132 KiB。服务随后自动重启为 1963720。原进程退出时还遗留多个 FFmpeg 子进程。

可重复证明的缺陷是：消费者推理异常后仅等待解码线程 5 秒，生产者可能永远堵在满队列上，保留图像、线程与解码子进程。修复为扫描局部取消信号、可取消的有界队列、继承调用任务的执行上下文和解码子进程回收。局部失败不会取消其他扫描；阻塞管道读取由所属进程的终止解除，超时再强制结束，回收后释放原有 CUDA 许可。失败批次不提交完成标记。

历史并行运动探测还会一次提交全部片段并保存整段像素列表，现在复用精扫的有界顺序预取。当前 device-day 生产路径未开启这条 keyframes-only 分支，不能把它描述为本次生产 OOM 的直接原因。

运行报告新增 `decoder_threads_alive_after_cleanup`。帧、时间、坐标、类别、推理策略、完成标记格式保持。正常结束不破坏调用方共享的分段同步屏障。

## 实证

- `49977f8` 在粗扫和精扫的消费者失败测试均不能关闭解码器；修复版通过。40 片段运动探测的超前解码测试同样旧版失败、新版通过。
- 实际子进程管道阻塞、忽略 SIGTERM、CPU/CUDA 许可路径、满/空队列、父任务取消、兄弟任务隔离均有失败场景测试。209 项通过，4 项原有源帧测试要求 FFmpeg 6+，在本机跳过。
- 同一真实视频的 16 秒 / 320 帧、同一第三人称 v5m TensorRT 引擎与参数，修复前后 JSONL SHA256 均为 `92ad9c37aaf7b9046df8be0ae4f04770de31dbf58b61606add8c3b4cb0f9577a`。本次 11.237 秒，旧回执 15.273 秒；共享负载不同，不据此声称性能提升。
- 真实 FFmpeg 解码后的故障注入通过生产 `DeviceDayModels._scan` 调度：两个子进程退出，残留解码线程 0，完成标记 0，整个调用 1.313 秒（含模型准备）。先前绕过调度器的故障脚本因未解析 `auto` 解码策略失败，原始失败保留，未作为成功证据。
- 变更文件 Ruff、compileall、diff 检查通过。全仓 Ruff 保留 `rtp_receiver.py` 原有两个问题，没有修改无关采集代码。

原始日志、真实回放、失败及成功回执在已核验 NAS 的 `LabPrism/evaluations/scan-cancellation-20260924-v1`。模型、输入身份见 `replay.json`，部署与回滚见 `runtime-deployment.json`。
