# 扫描缓存依赖与解码缓冲 · 2026-09-24

修正两个会拖累持续模型迭代与多路运行的问题：扫描缓存绑定所有角色/阶段的权重路径，导致无关换模也触发重算；解码队列只按帧数限制，原分辨率多路缓冲可能过大，已完成的预取 future 也可能继续持有尚未消费的画面。

本轮观察到生产 worker 被 systemd-oomd 终止并自动重启。该事实证明主机内存压力问题，不能仅据错误消息把全部压力归因于解码队列。以下修复收紧确定存在的像素缓冲上界，长期稳定性仍需生产观察。

## 实现

- 粗扫配置覆盖由 `scan_dependencies.phase_config` 同时供执行和缓存使用，避免两处选择规则漂移。
- `visioncortex-device-scan/2` 记录实际选中的视角、模型路径、后端与权重哈希。仅排除明确未使用的角色/阶段检测权重路径，保留未知设置及原片、时钟、窗口、采样率、阈值和相关代码身份。auto 模式失去引擎时，实际回退到 PT，缓存身份随之改变。
- 不复用未经验证的旧结构缓存。v1 缓存保留；首次进入 v2 命名空间会冷启动，之后无关角色换模才可命中已有 v2 结果。全局模型资格检查仍在设备日扫描前执行。
- 检测输出队列默认最多按 64 MiB 的原幅 BGR、灰度及前灰度估算帧数。1080p 下请求 64 帧会收紧为 6 帧；实际模型、画面尺寸与采样点不变。
- 一个视角的有序预取队列共享 64 MiB 原幅 BGR 预算。最多保留与解码 worker 数量相同的未消费分块；消费完成后才提交下一分块、释放旧队列和 future。
- 预算只覆盖这些队列，不覆盖模型、解码器内部缓冲、在途批次和其它系统缓存；单帧大于预算时仍允许一帧前进，不宣称这是整个进程的 RSS 上限。

## 检查与真实结果

181 项相关检查通过，覆盖角色/阶段缓存命中、auto 回退、有效权重/源/代码变化、结果篡改拒绝、预取顺序、失败传播与积压上界。新“完成 future 仍积压”用例在旧生产源码上确实失败，在修复后通过。两个旧 `RoleScanner.__new__` 测试漏初始化 NMS 计数器，同样在旧源码复现；仅补齐测试夹具，不改变推理行为。

修改文件 Ruff 与 compileall 通过。全仓 Ruff 仍有两个既有 `rtp_receiver.py` 问题（未使用 `uuid`、分号语句），本轮未修改该模块。

同一实际 1920×1080 片段、同一第三人称 v5m TensorRT 引擎，16 秒 / 320 帧 / 20 Hz，两个有序解码 worker：

| 范围 | 旧流程 | 新流程 |
| --- | --- | --- |
| 完整检测 JSONL | 320 帧 | 320 帧，逐字节一致 |
| 观测队列积压峰值 | 19 帧 | 5 帧（有效上限 6） |
| 单次扫描耗时 | 17.89 秒 | 15.27 秒 |
| 进程峰值 RSS | 1,505,288 KiB | 1,531,792 KiB |

短片未显示整个进程峰值 RSS 下降；单次时间差也不是稳定吞吐结论。更换未使用的第一人称引擎后，新缓存 0.007 秒命中完全相同的结果；实际第三人称引擎变化仍使身份失效。首次隔离运行因 CIFS 上临时协调数据库锁失败，失败日志保留；后续单进程验证使用既有 AW GPU 锁与显存/主机可用内存检查，未修改生产资源配置。
